# Meeting departure detection: acceptance and rollout

Status: native monitor and main-process policy implemented; UI adapters are gated pending signed packaged acceptance. No provider layout is enabled for inferred UI departure yet.

The prior app-level detector in PR #857 could infer closure from missing app/tab evidence. That is no longer an automatic-stop authority. A silent or muted meeting can release both microphone and output streams, and Pluto has already stopped such calls prematurely. **Audio-release-only stopping is prohibited.** The separately approved linked-calendar fallback requires an external cancellable warning after sustained quiet beyond the event end.

The passive Core Audio monitor reports per-app input/output activity and an exact application-instance termination notification. Electron binds a recording generation and provisional source, owns the departure state, and accepts exact instance termination only after the call source was explicitly confirmed or an accepted UI adapter observed the joined session. App-wide audio alone cannot confirm a call: unrelated Chrome playback followed by quitting Chrome leaves recording active. A sole active app may be suggested automatically, while multiple active apps require source selection. Chrome closure tracking is implemented but disabled: app-level Chrome audio cannot establish that the sole Meet tab is actually joined, so closing an unrelated tab could stop a recording. An inspected joined session never silently changes to another window or tab; unresolved same-app ambiguity or lost opaque session identity disables inferred UI stopping for that recording. An unknown, conflicting, stale, or failed inspection cancels pending confirmation. User End meeting also uses the shared stop path. Resource release must be acknowledged before reporting completion; normal journal sealing and transcript finalization continue afterward. `confirmed_departure_enabled=false` is the rollback switch; `auto_end_enabled=false` remains the user preference.

Chrome Meet, native Zoom, native Teams, and native Slack have separate adapter slots. Accessibility is an explicit opt-in for post-call UI inspection, separate from browser Automation; native polling never opens a permission dialog. The native helper sends only allowlisted UI tokens and opaque session IDs. The accepted-layout registry is deliberately empty until real signed-app observations establish stable joined/departed markers for a specific app version and supported language. An unsupported layout, denied permission, hidden window, missing control, or inspection failure means unknown and recording continues. Browser Automation plus app-level Chrome audio is insufficient to authorize exact-tab closure without tab-specific joined evidence.

## Release gate for each app/version/language

1. On a signed packaged build, observe a known joined state and a positive post-call state in the same call window or tab, with two positive departed samples at least one second apart. Preserve the exact accepted marker identifiers and version in the adapter registry. Do not ship a profile based only on fixture data or generic text.
2. Run a 30-minute silent break and a 30-minute muted break, including app releases of both input and output. Join muted and listen without speaking. Require zero premature stops before the scheduled end, and verify that quiet beyond a linked calendar end produces the cancellable warning rather than an immediate stop.
3. Hang up with the app/tab open. Verify prompt stopping only when positive departure evidence is available; otherwise verify continued recording and usable manual End meeting.
4. Exercise headset switches, network reconnection, helper restart, sleep/wake, hidden and minimized windows, denied Accessibility, unsupported layouts and language changes. Unknown observations must not stop or count toward two confirmations.
5. Exercise consecutive and simultaneous calls, multiple Chrome tabs/windows, and unrelated active apps. Session identity must prevent one call's departure from stopping another recording.
6. Verify source recording and transcript preservation, release acknowledgement, journal sealing, saved `end_reason`, and no completed-stop toast on failed release.

Roll out each adapter separately only after its matrix passes. Record the signed build, macOS version, app version, language, results, and accepted marker profile in the release evidence. Until then, app termination and explicit End meeting are the available confirmed-stop paths; leaving an app/tab open may require manual stopping.

## 2026-10-14 Meet smoke observation (not acceptance)

On the locally built, ad-hoc signed Pluto 1.0.0-rc.19 package on macOS 25.6, Chrome 155.0.8059.40 was observed in a disposable Meet call. The native helper reported a `leave_call` joined marker. During a 90-second muted sample, Chrome briefly reported both input and output inactive while later UI samples still reported `leave_call`. This reproduces the false-stop condition that prohibits audio-release-only decisions. One transient global audio-read failure also occurred; the coordinator now preserves a continuously observed bound session while clearing any pending confirmation.

After hang-up, the helper returned no allowlisted positive post-call marker. The user later clarified that the Meet tab had been closed, so this was not a valid post-call-UI sample. The joined and later samples used separate helper processes, so opaque tab identity was not continuous across them. The isolated packaged Pluto launch also failed transcription readiness with `parakeet_path_not_allowed`, preventing an end-to-end recording test there. This short smoke check did not run either 30-minute break or resource-release/journal acceptance. **The Meet UI adapter remains disabled.** A later dev recording bound Chrome but the tab-closure path never bound the Meet tab because its Accessibility joined marker was unavailable. Removing that gate made exact tab closure work in a local test, but app-level audio could bind an unrelated Meet tab; the path is now disabled pending tab-specific joined evidence and packaged acceptance.

# Calendar-end quiet fallback and remaining Zoom gap

The owner approved a separate calendar-linked fallback on 2026-10-15. It waits until two minutes after the linked event ends, requires two continuous minutes with both bound input and output inactive, and then shows an external twenty-second Keep recording / End now warning. Only an uncancelled warning may request `calendar_quiet_timeout`; the finished notice remains available for thirty seconds. This deliberately relaxes the earlier no-calendar-stop rule and needs signed acceptance with silent calls running past their scheduled end.

Ending a Zoom meeting while leaving Zoom open still has no accepted positive post-call adapter. The calendar fallback may eventually end a linked quiet Zoom recording, but it is not immediate Zoom hang-up detection. Keep the Zoom UI adapter disabled until the signed version and layout matrix passes.
